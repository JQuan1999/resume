## 四道"必杀题"——答不好这四道，其它答得再好也没用

### Q. 你说熟悉三大框架的"部署与调优"，具体怎么调的？

⚠️ **转岗者最容易翻车的一题，完整答法见 [01-大模型推理.md](01-大模型推理.md) 的 Q0。**
一句话记住：面试官问"怎么调优"，想听的是「**你怎么定位瓶颈**」，实验只是验证手段。
分三层答——**选型靠实验（但要有固定口径）/ 参数靠显存账 + prefill·decode 瓶颈判断 /
代码靠 profiling**，第三层直接甩 GR 的 D2H 案例。
**绝对不能说"哪个好用用哪个"。**

### Q. 你简历上都是部署和平台，你做过真正的推理优化吗？

这是转岗者最容易被质疑的点。**准备一个 60 秒的标准回答**：

> 做过两类。一类是框架层的：自研的 C++ 推理引擎里，我实现了动态 batch 的凑批策略——
> 用无锁队列做批量出队，不足最小批量时按超时分段续取，在延迟约束下把 GPU 利用率提上去，
> 这个框架现在支撑 200 多个模型在线。另一类是解码热路径的：做生成式检索的约束解码时，
> 我通过 profiling 发现每个 decode step 都有两次 15 万维词表 logits 的 D2H 拷贝加 CPU 上的
> log_softmax，这是个强制流同步点，把它重构成全程 GPU 计算、显存驻留、生成结束时一次
> gather 取标量，每请求的设备同步次数从 O(生成长度) 降到 1 次。
> 那个项目最后因为整体延迟还是不达标没上线，但这个优化本身是实打实的。

**为什么这么答**：先给"框架层 + kernel 调用层"两个层次，再各给一个具体动作，
最后主动交代没上线。主动说 > 被问出来。

### Q. 你对推理的理解，和做业务后端有什么本质区别？

> 后端优化的是 IO 和并发调度，瓶颈通常在网络、锁、内存分配；
> 推理优化的是计算和显存，瓶颈在算术强度、显存带宽、host-device 同步和 batch 效率。
> 最大的差别是——后端加机器基本线性扩，推理加卡不一定线性扩，因为 KV Cache 显存、
> batch 组织方式和长短请求的调度会互相牵制。所以推理更需要先测再改：
> 先分清是 prefill 瓶颈还是 decode 瓶颈，是算力打满还是带宽打满，再决定动哪里。

### Q. 你用过 vLLM，那你知道它为什么快吗？

见 [01-大模型推理.md](01-大模型推理.md) Q2/Q3。**你读过 nano-vLLM 源码，这题是你的送分题，
一定要答到 block 粒度和链式哈希，把它从"用过"变成"读过实现"。**

## 使用方法

对"硬编"的容忍度极低。
